# Game Visual Design

先从玩家在每个阶段必须做出的决定反推界面，再确定信息层级、屏幕位置、视觉语言和反馈。美观不是给玩法外面套皮，而是让玩家更快看懂危险、收益、节奏与下一步行动。

## 责任边界

- 本 Skill 拥有游戏品类识别、玩家注意力预算、HUD 信息架构、屏幕区域分配、视觉层级、图标语义、反馈优先级和画面验收。
- `godot-ui`、`hud-system` 与 `responsive-ui` 负责把方案实现为 Godot Control、CanvasLayer、Theme 和响应式布局。
- `builda-vector-art` 是 SVG 素材生产的唯一 owner；本 Skill 只输出资产 brief，不直接发明 SVG 文件规范或绕过其校验。
- `tween-animation`、`particles-vfx`、`shader-basics` 与 `audio-system` 负责实现已经定义好的反馈。
- 先读取项目根 `AGENTS.md`、玩法脚本、主场景、现有 Theme/字体/素材和最新可运行画面。当前项目事实优先于通用品类范式。

需要建立美术方向、下达素材 brief 或审查素材库时，同时读取 [references/art-asset-production.md](references/art-asset-production.md)。

## 设计工作流

### 1. 还原玩法，而不是先画界面

用一段话写清：

```text
玩家幻想：玩家想成为谁、获得什么感觉
核心循环：观察 -> 决策 -> 操作 -> 反馈 -> 成长
阶段：战斗中 / 波次间 / 商店或升级 / 失败与复盘
压力来源：时间、敌人、资源、空间、精度或信息不确定性
主要输入：键鼠、手柄或触屏
```

没有真实可玩循环时，先建立最小假设并明确标注，不能用一个通用 RPG HUD 掩盖玩法尚未成立。

### 2. 建立信息优先级

为每条候选信息填写：

| 字段 | 问题 |
| --- | --- |
| 玩家决策 | 看到它以后玩家会改变什么操作？ |
| 紧迫度 | 必须立即反应、数秒内处理，还是回合后查看？ |
| 更新频率 | 每帧、高频事件、偶发事件或只在阶段切换时变化？ |
| 忽略代价 | 会死亡、损失收益、错过机会，还是没有后果？ |
| 最佳载体 | 世界内反馈、固定 HUD、临时提示、菜单详情或音效？ |

按以下层级收敛：

- **T0 世界行动**：角色、敌人、弹道、攻击范围、路径和交互目标，必须优先保住可视空间。
- **T1 生死与时机**：生命、重大危险、关键计时、Boss 阶段，必须一瞥可读。
- **T2 当前策略**：经验、资源、武器状态、连击、波次进度，稳定但不能抢过战场。
- **T3 复盘详情**：完整属性、说明、历史和比较，只在暂停、商店或详情层展示。

如果一个元素不能改变决策、确认反馈或建立氛围，就删除，不因为“其他游戏都有”而保留。

### 3. 分配注意力与屏幕区域

- 先标出玩家高频注视区、敌人可能进入区、移动方向和必须看到的落点/路径。
- 保护主要行动区；来自四面八方的竞技场玩法尤其不能使用常驻大侧栏或厚底栏。
- 高频且关键的信息放在视线迁移短、位置稳定的区域；低频信息靠边、按需出现或进入独立阶段。
- 同一语义组成一个视觉簇，不把生命、等级、资源和武器散成多个无关角标。
- 固定 HUD 使用锚点和安全边距；世界空间信息跟随对象，但必须避免大量标签重叠。
- 位置选择必须写出玩法理由。需要具体品类范式时读取 [references/genre-layouts.md](references/genre-layouts.md)。

### 4. 建立视觉语言

先写一句视觉命题，例如：

```text
圆润玩具轮廓 + 高对比危险色 + 纸贴式升级卡，表达轻松但高压的竞技场生存。
```

再定义：

- 形状语言与游戏幻想；
- 背景、主体、奖励、危险、可交互、不可用状态的颜色语义；
- 字体层级、数字字体和中文可读性；
- 图标轮廓、填充/描边、光影方向和视觉重量；
- 面板密度、圆角/切角、边框与留白；
- 动效节奏：平时克制，重要事件才提升幅度。

图标、数字、标签和组件的组合规则见 [references/visual-hierarchy.md](references/visual-hierarchy.md)。禁止每个系统各做一套颜色、描边和动画。

### 5. 把反馈映射到玩法事件

为关键事件建立状态表：

| 事件 | 必须被感知的事实 | 主通道 | 辅通道 | 强度/持续时间 |
| --- | --- | --- | --- | --- |
| 受击 | 伤害来源与剩余生存空间 | 角色/屏幕反馈 | 生命变化、音效 | 随危险程度变化 |
| 拾取 | 已获得且归入哪类资源 | 世界吸附/飞入 | 计数跳变、音效 | 高频时合并 |
| 升级 | 新决策窗口已打开 | 阶段切换 | 标题、卡片入场 | 明确但不拖沓 |
| 冷却完成 | 现在可以行动 | 图标恢复 | 微光、短音效 | 不遮挡战斗 |

同一事件最多选择一个主通道和必要的辅助通道。不要让镜头震动、闪白、粒子、大字、音效和 HUD 跳动同时满强度播放。

### 6. 输出可实现合同

在编码和制图前输出：

1. **视觉命题**：一句话说明气质、材质和能量。
2. **阶段与信息表**：每个阶段只保留当下需要的信息。
3. **HUD 区域图**：用 ASCII 或简图标出保护区、信息簇与弹层方向。
4. **组件状态表**：normal、focus/hover、pressed、disabled、warning、critical、reward。
5. **资产清单**：语义名称、用途、目标尺寸、状态、形状语言和复用关系。
6. **反馈表**：事件、主通道、辅助通道、持续时间和性能上限。
7. **验收场景**：平静、普通战斗、峰值混乱、低血量、阶段切换和目标分辨率。

资产清单交给 `builda-vector-art`；布局交给 `godot-ui`/`hud-system`/`responsive-ui`；反馈交给对应动画、粒子、Shader 和音频 Skill。

素材进入项目之前，先区分复用、变体、独有和暂缓资产，记录来源与许可证，并用真实导入和运行画面检查尺寸、透明边缘、方向、状态覆盖与风格一致性。文件存在、缩略图好看或资产数量达标都不代表可用。

### 7. 用真实运行画面验收

不能只审查 `.tscn` 或 SVG。构建并检查目标 Web 画面，按 [references/visual-review.md](references/visual-review.md) 验证：

- 两秒内能否找到生死、目标和收益信息；
- 峰值战斗时 UI 是否遮挡敌人、弹道、落点或路径；
- 模糊、缩小或运动时，层级是否仍然成立；
- 颜色之外是否还有形状、文字、位置或动效编码；
- 新资产是否像同一个游戏，而不是素材拼盘；
- 动效是否帮助理解状态，而不是持续抢夺注意力。

发现问题后回到信息优先级或区域分配修正，不用增加更多装饰掩盖结构问题。

## 硬规则

- 不从组件库、默认 HUD 模板或现有素材数量反推设计。
- 不把“美观”简化为渐变、发光、圆角卡片、描边或更多粒子。
- 不把所有数值常驻屏幕；战斗决策之外的数据进入详情层或阶段间界面。
- 不用 UI 弥补世界内危险提示不足；攻击范围、敌人方向和可拾取物应优先在游戏世界中读懂。
- 图标不能只靠颜色区分，同族图标必须共享网格、轮廓和视觉重量。
- 高频事件必须合并和限流，不能让伤害数字、拾取提示或通知淹没行动区。
- 不凭品类名称机械复制某款游戏；范式只是起点，最终布局必须由当前核心循环证明。
- 没有在普通与峰值状态的真实画面中验证，就不能宣称视觉设计完成。
