# Runtime Visual Review

## 必测画面

至少检查：

1. 刚进入游戏、没有事件的平静状态；
2. 普通强度的核心循环；
3. 敌人、弹道、拾取和反馈同时出现的峰值状态；
4. 低血量、资源不足或倒计时临界状态；
5. 升级、商店、暂停或阶段切换；
6. 项目支持的最小、基准和最大画布/窗口比例。

## 两秒扫视测试

隐藏实现细节，只看运行截图两秒，然后回答：

- 玩家是谁、当前目标是什么？
- 最大危险在哪里？
- 还能承受多少风险？
- 现在最值得做的动作是什么？
- 刚才发生了什么收益或损失？

答案依赖阅读长文、寻找多个角落或猜测颜色时，信息层级不合格。

## 遮挡检查

- 标出角色周围、主要来敌方向、弹道、落点、路径和目标对象。
- 检查常驻 UI、弹层、伤害数字、通知和工具提示是否进入这些区域。
- 在峰值状态检查多个临时元素叠加，而不是只看每个组件单独出现。
- 世界空间标签必须避让或聚合；离屏目标采用方向指示，不在边缘堆文字。

## 层级检查

- 将画面缩小到 25%：T1 信息仍应最先被看到，装饰不应成为主角。
- 对画面做轻度模糊：主要信息簇和危险轮廓仍可区分。
- 临时转为灰度：危险、奖励、可用与禁用仍有形状/明度差异。
- 隐藏 HUD：世界中的敌人、攻击、拾取和交互是否仍可理解。
- 隐藏装饰：核心玩法信息是否仍完整；若是，装饰应保持克制。

## 一致性检查

- 图标是否共享网格、描边、光影和视觉重量；
- 面板、按钮、数字和世界素材是否属于同一形状语言；
- 相同语义是否始终使用相同颜色、位置和反馈；
- 新素材是否复用既有 token，而不是出现新的随机圆角、阴影和渐变；
- 中文字体、字号、描边和截断在真实 Web 导出中是否正确。

## 反馈检查

- 玩家输入后是否立即获得可见或可听的确认；
- 受击是否能判断来源、强度和结果；
- 拾取是否能判断物品最终归入哪里；
- 冷却、升级和阶段完成是否明确改变可行动状态；
- 高频事件是否合并，动画是否在短时间内回归稳定；
- 镜头、Shader、粒子、UI 和音效是否争抢同一个事件。

## 完成条件

只有当普通和峰值状态都能通过扫视、遮挡、层级、一致性与反馈检查，并且修改已经在目标 Godot Web 构建中验证，才可以宣称视觉设计完成。
