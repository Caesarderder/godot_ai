# UX Design

先定义玩家为何来到这个界面、要完成什么，再设计信息、布局和交互。产物必须让设计、美术、Godot 实现和 QA 对“完成”有同一个可验证定义。

本 Skill 由 Claude Code Game Studios 的 `ux-design` 工作流适配而来；来源与许可见 [references/upstream-license.txt](references/upstream-license.txt)。

## 责任边界

- 本 Skill 拥有玩家目标、用户流程、信息架构、导航、交互模式、输入映射、状态、无障碍、本地化约束和 UX 验收标准。
- `game-visual-design` 负责颜色、字体、形状、材质、视觉层级和运行画面美感；UX 规格只定义视觉需要表达什么。
- `godot-ui`、`responsive-ui` 与 `hud-system` 负责 Godot 4.6.x Control、Theme、CanvasLayer、焦点和响应式实现。
- `builda-vector-art` 负责 SVG 资产生产；本 Skill 只记录资产语义和状态需求。
- 本 Skill 默认只产出或修订 `design/ux/` 下的设计文档。除非用户同时要求实现，不修改场景、脚本、Theme 或资产。

## 入口与产物

根据用户参数选择模式：

| 参数 | 模式 | 默认产物 |
| --- | --- | --- |
| `hud` | HUD 设计 | `design/ux/hud.md` |
| `patterns` | 交互模式库 | `design/ux/interaction-patterns.md` |
| 界面或流程名称 | 单屏/跨屏 UX 规格 | `design/ux/<kebab-case-name>.md` |
| 未指定 | 从当前任务和工程判断；仍不明确时只问一个最能解锁设计的问题 | 确认后决定 |

用户只要求分析或讨论时，不默认写文件；用户明确要求设计、创建或更新时，可在展示目标路径与范围后直接落盘。

## 1. 先读真实上下文

从最小相关集合开始，存在才读取：

1. 项目根 `AGENTS.md`、`project.godot` 和当前任务说明；
2. 游戏概念、GDD、玩家旅程或现有产品设计文档；
3. `design/ux/` 中相邻界面和交互模式；
4. 当前主场景、UI 场景、Theme、字体和输入映射；
5. 最新可运行画面、用户提供的参考图或明确的视觉方向；
6. 无障碍、目标分辨率、键鼠/手柄/触屏与本地化要求。

不要因为缺少某份模板而停止。记录缺口，将必须决定的事实与可延后验证的假设分开。

先给出简短上下文摘要：

```text
设计对象：
玩家到达时的目标与状态：
入口和出口：
目标平台/分辨率：
主要输入：
已有相关界面或模式：
已知约束：
仍需确认：
```

## 2. 检查新建还是接续

若目标文件已存在，逐节标记：

- **已确认**：内容具体且仍与代码/设计事实一致；
- **待验证**：已有方案，但缺运行画面、输入或实现证据；
- **待补充**：空白、占位或缺关键状态；
- **冲突**：与当前 GDD、代码、相邻界面或输入方式不一致。

只修改用户要求的范围以及待补充部分；不得静默覆盖已确认决定。遇到冲突先给出证据、影响和 2–3 个可选处理。

## 3. 用决策循环逐段设计

每个有实质取舍的章节使用：

```text
上下文 -> 关键问题 -> 2–3 个选项与取舍 -> 用户决定
-> 草案 -> 核对 -> 写入
```

一次只追问会改变布局、流程或范围的关键问题。能够从项目事实得到的答案不要反问用户。审美偏好无法从 Art Bible、参考图或现有画面判断时，再让用户选择。

## 4. 单屏或流程规格

使用 [references/ux-spec-template.md](references/ux-spec-template.md)，按以下顺序完成。

### 4.1 玩家需要与上下文

明确：

- 玩家来到这里想完成什么；
- 刚才在做什么，是否紧张、探索、比较或复盘；
- 没有这个界面或它难以使用时，会损害什么体验；
- 它位于导航层级中的位置。

用一句玩家视角陈述收敛：

```text
玩家来到这个界面，希望在 <情境> 下，以 <成本/时间> 完成 <目标>。
```

### 4.2 入口、出口与流程

列出每个入口的触发方式和携带状态，以及每个出口、返回行为和不可逆影响。跨屏流程用 Mermaid 或紧凑文本表达；单屏不为画图而画图。

### 4.3 信息架构与布局

先列出全部信息，再分为：

- 必须立即看到；
- 当前任务需要；
- 可按需展开；
- 不应在此界面出现。

信息层级确认后，才提出 2–3 个区域布局。每个布局都要说明注意力路径、对玩法画面的遮挡、输入效率和小屏风险。

最终记录：

- 布局区域；
- 每区组件；
- 组件内容和交互性；
- 复用或新增的交互模式；
- 必要时的 ASCII 线框图。

### 4.4 状态与变体

至少覆盖适用的：

- default / loading / empty / populated / error；
- locked / disabled / unavailable；
- first-use / tutorial；
- success / confirmation / destructive warning；
- 最小与最大数据；
- 不同分辨率、宽高比与输入设备。

每种状态写明触发条件、变化内容、可用操作、恢复路径和反馈。

### 4.5 交互与输入映射

为每个可交互组件记录：

| 组件/动作 | 键鼠 | 手柄 | 即时反馈 | 结果/事件 | 焦点去向 |
| --- | --- | --- | --- | --- | --- |

所有主要动作必须能在不依赖鼠标精确定位的情况下完成。定义默认焦点、方向邻居、返回行为、弹窗焦点约束和输入方式切换。

### 4.6 数据与事件

界面不拥有游戏状态。对每项展示数据记录 owner、读取方式、更新触发、空值行为；对每项玩家动作记录发出的命令或事件、负载与失败反馈。

### 转场、动画与反馈

记录进入、退出、状态变化和关键操作反馈。动效必须说明目的、持续时间、可跳过或 reduced-motion 降级；高频状态不能依赖持续抢眼动画。

### 4.8 无障碍与本地化

至少检查：

- 键盘和手柄完整可达，焦点始终可见；
- 颜色不是唯一编码；
- 中文在最小字号和运动画面中仍可读；
- 文本缩放、长文本、40% 扩展和 CJK 短文本；
- 动效可降级，闪烁受控；
- 图标具有文字、形状或可读标签替代；
- 日期、数字、单位和复数规则可本地化。

### 4.9 验收标准

至少包含下列可二元判断的条件：

- 核心玩家目标；
- 入口、退出和返回；
- loading/empty/error 中适用的状态；
- 键鼠与手柄；
- 最小和最大目标分辨率；
- 无障碍；
- 数据更新和失败恢复；
- 与相邻界面/交互模式一致。

禁止“看起来高级”“操作流畅”这类无法独立验收的措辞；改为具体画面、动作、时限或状态结果。

## 5. HUD 模式

使用 [references/hud-design-template.md](references/hud-design-template.md)。

### 5.1 HUD 哲学

在“近乎无 HUD、极简、信息密集、自适应”中选择方向并说明玩法理由。

### 5.2 信息盘点

收集所有系统希望展示的信息，分类为：

- **常驻**：实时决策不可缺少；
- **情境出现**：战斗、交互或危险时出现；
- **按需查看**：玩家主动打开；
- **世界/音频表达**：不进入固定 HUD。

若常驻项与 HUD 哲学或行动画面冲突，减少常驻项或改为自适应，不用缩小字号硬塞。

### 5.3 区域与动态行为

保护角色、敌人、弹道、落点和交互目标等行动区。为每个 HUD 元素记录区域、优先级、数据 owner、显示条件、更新频率、临界状态、动画和输入变体。

定义探索、普通战斗、峰值战斗、对话/过场、暂停、低血量和阶段切换时的密度变化，并设置同时可见元素与高强度强调的视觉预算。

## 6. 交互模式库模式

先从已有 UX 规格中提取重复组件和行为，再为每个模式记录：

```markdown
### 模式名称
- 类别：
- 使用界面：
- 解决的问题：
- 结构与状态：
- 键鼠/手柄输入：
- 视觉、声音和动效反馈：
- 无障碍：
- 适用条件：
- 不适用条件：
- Godot 实现提示：
```

至少审视 button、toggle、slider、tab、list/grid、modal/dialog、toast、tooltip、progress、scroll 和返回行为。不要为了“完整”添加当前游戏不需要的复杂模式。

## 7. 交叉检查与交付

提交规格前检查：

1. 每条相关 GDD UI 要求是否有对应组件、状态或明确排除理由；
2. 入口与出口是否和相邻界面一致；
3. 新交互模式是否加入模式库或标为待办；
4. 每个数据依赖是否有 loading/empty/error 或不适用说明；
5. 键鼠、手柄、目标分辨率、无障碍和本地化是否闭合；
6. 设计决定是否来自项目事实、用户选择或显式假设。

输出简短交付摘要：完成文件、已确认决定、待验证假设、实现依赖和下一步。

后续路由：

- 需要视觉语言和真实画面美化时使用 `$game-visual-design`；
- 需要 Godot Control/Theme 实现时使用 `$godot-ui`；
- 需要多分辨率适配时使用 `$responsive-ui`；
- 需要 HUD 运行时实现时使用 `$hud-system`；
- 需要最终功能与运行证据时回到用户任务并运行仓库现有测试与真实运行检查。

## 完成边界

- 规格写完只代表 UX 设计完成，不代表 Godot UI 已实现。
- `.tscn` 能打开不代表输入、状态、分辨率和可读性合格。
- 自动测试不能证明审美、注意力层级或峰值玩法画面；视觉结论必须由真实 Godot Web 运行画面支持。
- 未解决问题必须写出 owner、影响和验证方式，不能用默认组件悄悄代替设计决定。
