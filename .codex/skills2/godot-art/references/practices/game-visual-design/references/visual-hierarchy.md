# Gameplay Visual Hierarchy

## 从语义到视觉重量

视觉重量由面积、对比度、位置、运动和持续时间共同决定。只为 T1 生死/时机信息同时使用多个强信号；T2 策略信息通常只需要稳定位置和清晰数字；T3 详情不应常驻战斗画面。

## 屏幕区域

- **行动中心**：角色、瞄准点、道路消失点、谜题棋盘或敌人意图的主要区域。避免不透明常驻 UI。
- **节奏顶部**：波次、时间、目标和全局阶段，适合短而稳定的信息。
- **操作底部**：手牌、技能、建造栏等与输入直接对应的元素；只有确实需要操作时才占据空间。
- **状态角落**：生命、资源、小地图等稳定信息簇。每个角落只承担一个主语义。
- **上下文空间**：跟随对象的提示、伤害数字和交互信息，必须合并、避让和限流。

不要依据固定坐标选择区域。先看镜头、角色位置、来敌方向、手部遮挡和输入设备，再用 Godot anchors/containers 实现。

## 信息簇

- 相同决策中的信息靠近，例如生命值、护盾和治疗资源；不要仅因数据 owner 不同而拆散。
- 每个常驻簇优先控制在 3 到 5 个视觉单元，更多内容进入展开层。
- 一个簇只有一个主数字或主状态，其他内容通过较小字号、低对比或图标补充。
- 对齐数字基线和图标光学中心；连续变化的数字预留宽度，避免布局跳动。
- 不用面板包住每个元素。背景只在复杂画面中确实能提高可读性时出现。

## 图标与文字

- 图标承担快速分类，数字承担精确量，短标签承担学习和消歧。
- 新颖或项目专有图标先配短标签；玩家学会后可在高频战斗层隐藏标签。
- 同族图标共享 viewBox、视觉边距、描边、圆角和高光方向，但必须用轮廓区别语义。
- 图标通常位于数字或标签的阅读起点；计量条中的图标靠近填充起点，减少匹配距离。
- 资源、危险、奖励和不可用状态不能只换颜色；同时改变轮廓、徽记、文字或动效。
- 小尺寸优先强剪影和 1 到 2 个内部特征，不把插画缩小冒充图标。

## 字体与数字

- 中文使用项目内置并经过验证的字体，不能依赖系统字体。
- T1 数字使用稳定字宽、清晰描边/背景和短格式；T2/T3 逐级降低字号与对比。
- 运动画面中的文字优先短词和数字，完整句子只在安全阶段出现。
- 避免全大写英文、过度字距、细字重和长阴影破坏中文可读性。

## 色彩与材质

- 先确定世界画面的明度和饱和度，再选择 HUD 的对比策略。
- 背景/中性、主要交互、奖励、危险、禁用形成稳定语义；不要让稀有度色和危险色冲突。
- 高饱和色是注意力预算，不是装饰。常驻大面积高饱和会让真正的危险失效。
- UI 材质和形状应回应游戏世界：木质经营、纸贴构筑、机械战术、玩具竞技场等，而不是通用科技面板。

## 动效

- 出现说明“这里有新状态”，位移说明“信息从哪里到哪里”，缩放说明“重要性变化”，颜色说明“性质变化”。
- 战斗常驻元素只做微幅、短时反馈；阶段切换才允许较完整的入场序列。
- 高频事件合并，避免每次拾取或伤害都触发完整动画。
- 动效结束后必须回到稳定、易读的静止状态，并提供 reduced motion 降级。

## 视觉预算

为一个战斗帧限制：

- 同时高强度强调不超过一个主事件；
- 同时出现的临时通知优先不超过三条；
- 行动中心的文字和数字只保留能改变即时决策的内容；
- 非关键面板尽量透明、隐藏或移入阶段间界面；
- 峰值粒子、伤害数字、闪光和镜头效果必须共同评估，而不是各系统分别达到上限。
